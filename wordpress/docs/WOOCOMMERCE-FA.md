# پیکربندی تجارت واقعی WooCommerce

منبع محصولات، دسته‌ها، قیمت، موجودی، variation، کوپن، سبد، تسویه، سفارش و حساب فقط WooCommerce است. Core تنظیمات تماس/پیام/علاقه‌مندی و مهاجرت را نگه می‌دارد. JavaScript قالب فقط نمایش/منو/اسلایدر را کنترل می‌کند؛ مبلغ ارسالی مرورگر مبنای قیمت سفارش نیست.

## واحد پول

| انتخاب | ورود ۱۰۰۰۰۰ | نمایش/سبد/سفارش جدید |
|---|---|---|
| IRT — تومان ایران | ۱۰۰۰۰۰ تومان | همان ۱۰۰۰۰۰ تومان |
| IRR — ریال ایران | ۱۰۰۰۰۰ ریال | همان ۱۰۰۰۰۰ ریال |

Core فقط ثبت واحد IRT و نمادهای فارسی را اضافه می‌کند. هیچ price filter برای تبدیل عدد ندارد. واحد پیشخوان و ایمیل از WooCommerce می‌آید. تغییر انتخاب واحد **قیمت‌های ذخیره‌شده را تبدیل نمی‌کند**؛ سفارش قبلی واحد خودش را حفظ می‌کند. قبل از تغییر روی فروشگاه فعال، پشتیبان، برنامهٔ بازبینی تمام ارقام و سازگاری درگاه داشته باشید. کاتالوگ مرجع فقط IRT است.

## محصولات

محصولات ← افزودن/ویرایش: قیمت، فروش ویژه، زمان‌بندی، موجودی، ویژگی‌ها، تصویر شاخص، گالری و دسته‌ها. محصول متغیر بومی از ویژگی با گزینهٔ «برای متغیرها استفاده شود» و variationهای قیمت‌دار/موجود ساخته می‌شود. قالب فرم variation رسمی را نمایش می‌دهد؛ نیازی به تغییر PHP نیست. رنگ‌های واردشدهٔ منبع، ویژگی ساده با موجودی مشترک هستند.

برندها از taxonomy بومی `product_brand` استفاده می‌کنند؛ روی نسخهٔ فاقد آن، مقدار واردشده در metadata نگهداری و فیلتر می‌شود. فروشگاه از جست‌وجو، برند، بازه قیمت، موجود/ویژه، مرتب‌سازی و صفحه‌بندی بومی استفاده می‌کند. محصولات بدون موجودی قابل سفارش نیستند مگر مدیر عمداً backorder را در WooCommerce مجاز کرده باشد.

## ارسال، تخفیف، حساب

- پیکربندی ← ارسال: کشور/منطقه، روش نرخ ثابت/رایگان و شروط را خودتان تنظیم کنید. متن تبلیغاتی قالب جای تنظیم روش ارسال را نمی‌گیرد.
- بازاریابی ← کدهای تخفیف: محدودیت مبلغ، محصول، تاریخ و مصرف را در WooCommerce تعیین کنید.
- حساب‌ها و حریم خصوصی: خرید مهمان، ثبت‌نام از حساب/تسویه و سیاست نگهداری را انتخاب کنید. فعال نبودن ثبت‌نام یک تنظیم مدیر است، نه دکمهٔ ساختگی ثبت‌نام.
- پیگیری با شمارهٔ سفارش و ایمیل صورتحساب از shortcode بومی انجام می‌شود. حساب کاربر فقط سفارش‌های همان کاربر را می‌بیند.

## پرداخت آفلاین و درگاه آینده

برای staging از پرداخت هنگام دریافت یا انتقال مستقیم بانکی با برچسب صریح آزمایشی استفاده کنید. سفارش، محاسبه، موجودی و وضعیت همچنان در WooCommerce ثبت می‌شوند؛ این تست **پرداخت بانکی واقعی نیست**. هیچ پرداخت واقعی یا تراکنش شبکهٔ بانکی در QA این پروژه انجام نشده است.

برای درگاه آینده:

1. افزونهٔ معتبر سازگار با نسخهٔ WooCommerce، HPOS و واحد IRR/IRT انتخاب کنید.
2. مستندات واحد مورد انتظار API درگاه را بررسی کنید. اگر API ریال می‌خواهد، تبدیل باید فقط در افزونهٔ درگاهِ معتبر و در مرز درخواست پرداخت انجام شود، نه تغییر کور قیمت کل فروشگاه.
3. sandbox درگاه: callback امضاشده، مبلغ/واحد/شناسه، تکرار callback، لغو، خطا و بازگشت را آزمایش کنید.
4. یک پرداخت واقعی کنترل‌شده فقط با مجوز مالک، سپس تطبیق رسید درگاه/سفارش/موجودی/ایمیل.
5. تا آن زمان هیچ نشان یا ادعای «درگاه تأییدشده/پرداخت موفق واقعی» نمایش ندهید.

## محیط QA و مرز نتایج

WordPress واقعی 7.1.4، PHP-WASM 8.3.36 و WooCommerce 11.2.2 از سورس رسمی تگ مشخص‌شده در `reports/woocommerce-build.json` استفاده شده‌اند. نسخهٔ رسمی WC و dependencyهای قفل‌شده ساخته شده‌اند؛ این build با hash ZIP انتشار رسمی یکسان ادعا نمی‌شود و **داخل دو ZIP هشتگ نیست**.

SQLite Integration محیط QA جای MySQL/MariaDB هاست را نمی‌گیرد. گزارش لاگ آن ناسازگاری بعضی queryهای Action Scheduler را نشان می‌دهد؛ بنابراین cron، صف کارهای پس‌زمینه/analytics و ارتقاهای زمان‌بندی‌شده تأیید نشده‌اند. برای فروش واقعی روی دیتابیس پشتیبانی‌شدهٔ هاست تست کنید. این محدودیت با دستکاری هستهٔ WooCommerce پنهان نشده است.
